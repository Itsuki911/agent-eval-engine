3. テスト作成・実行ルール
==================================================
【自動テスト（構文・エラーチェック）】
・各コードファイルのエラーがないか、構文チェックなどを目的とするテストを実行し、それに伴うテストコードを作成してください。
・これは人間が手動で目で確認する単体テスト、統合テスト、E2Eテストとは異なります。

【手動テストケースの作成（Markdown）】
・人間が手動で確認するテストも、作成したコード・機能の内容に沿って書いてもらいます。
・`tests` フォルダ内の4つのフォルダ（UT / IT / RT / E2E）のうち、作成した機能、UIの内容、開発の進捗状況を考慮して、最適な場所に最適な内容をMarkdownで記載してください。

■ テストケースID命名規則： `{分類}-{機能}-{連番}`

■ 分類コード表：
| 分類 | コード |
|---|---|
| Unit | `UT` |
| Integration | `IT` |
| Regression | `RT` |
| End-to-End | `E2E` |

■ テストケースの記載規則：
・タイトルは「対象 + 操作 + 期待する結果」で書く
・手順は命令形で、1手順につき1操作にする
・期待結果は判定可能な表現にする
・正常系・異常系・境界値を明記する
・各テストケースには、期待結果を再現する実行コマンドをコードブロックで記載する
・手動確認用のpytestコマンドは`-v`を指定し、テスト名と結果を表示する

■ 運用ルール：
- 新機能には最低1件の正常系と1件の異常系を作る。
- 不具合修正では、再発を防ぐ `RT-...` の回帰テストを必ず追加する。
- 実装やAPI仕様が変わったPRでは、関連する手動テストの更新有無を確認する。
- Fail や Blocked の実施記録は消さず、原因・Issue番号を備考へ残す。

■ 機能単位の分割：
e2eやintegrationなど、項目が増えたら機能単位に分割します。
（例）
tests/e2e/manual/
├─ authentication.md
├─ evaluation-job.md
└─ result-export.md
